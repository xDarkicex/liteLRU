\begin{abstract}
Concurrent approximate LRU structures often serialize cores on shared metadata. We investigate whether a bounded-probe, 64-way set-associative cache combining bit-sliced S3-FIFO eviction, single-pointer immutable payloads, and contention-aware admission load-shedding can achieve both high scan-resistant hit rates and predictable concurrency costs without centralized locking in a garbage-collected runtime. We present \texttt{liteLRU} (v2), a fixed-capacity cache in Go whose compact synchronization metadata (SWAR signatures, Small/Main partitions, 2-bit bit-sliced frequencies, 128-bit resetting Ghost Bloom filter, and writer ownership masks) packs into 128-byte off-heap \texttt{mmap} chunks (2~bytes/slot), while key/value snapshots reside on the Go heap behind a single \texttt{atomic.Pointer[cacheEntry]} per slot (8~bytes/slot). Reads provide single-pass lock-free bounded-probe execution with zero heap allocations on hits when supplied a caller buffer and never mutate that buffer on misses; writes are best-effort, non-linearizable cache insertions/updates capping per-slot ownership CAS retries at $R=10$. Across 10-run hardened evaluations on an 8-core Apple M2 (24 GB RAM), \texttt{liteLRU} sustains \textbf{51.32M~ops/s} on the uniform 80/20 baseline ($3.14\times$ \texttt{otter v1.2.4} and $7.29\times$ \texttt{Mutex LRU}, with 500~ns sampled p99 vs.\ 9.90~\textmu s for \texttt{otter}), leads \texttt{otter} across immutable insert-on-miss workloads (\textbf{128.59M vs.\ 113.74M~ops/s} at $N=1\text{k}$ where \texttt{otter} achieves 99.94\% vs.\ 99.19\% hits; \textbf{56.29M vs.\ 9.12M~ops/s} at \texttt{cap=16384, N=100k}) and direct overwrite contention (\textbf{26.57M--32.51M} effective ops/s, $5.33\times\text{--}6.58\times$ \texttt{otter} with 4.67\%--5.30\% overlapping-slot drops vs.\ full queuing), achieves higher matched-capacity Zipfian hit rates than \texttt{otter} across all six $(s, \text{cap})$ points ($+0.05$ to $+2.38\text{ pp}$), and delivers a $1.30\times$ end-to-end throughput advantage under an explicit 5~\textmu s backend miss penalty, while matched-capacity loopback \texttt{net/http} throughput remains TCP/serialization bound (76.4k--80.7k vs.\ 82.1k--82.9k~req/s for \texttt{otter}). A controlled 3-policy comparison on the identical v2 engine validates retaining \texttt{PolicyS3FIFO} as the default over \texttt{PolicyCLOCK} and \texttt{PolicyCLOCKPlus}.
\end{abstract}

\section{Background: The Hardware Model}

To reason about concurrent cache design, we first establish a precise model of the hardware execution environment.

\subsection{The CPU Cache Hierarchy}

Modern multi-core processors organize memory into private L1 caches (typically 32--64 KiB, $\sim$4--5 cycles) backed by larger L2/L3 tiers and main memory ($\sim$200--300 cycles), so an L1 miss is over an order of magnitude more expensive than an L1 hit. L2/L3 sharing varies across targets: conventional x86\_64 servers typically attach private L2 caches (256 KiB--1 MiB) per core beneath a shared multi-megabyte L3 cache, whereas our Apple M2 evaluation CPU groups its 8 cores into a 4-core Performance cluster (shared cluster L2) and a 4-core Efficiency cluster (smaller shared cluster L2) backed by a System Level Cache (SLC).

The fundamental unit of coherency is the \textbf{cache line}, dependent on the target platform architecture (e.g., $L=64$ bytes on x86\_64, $L=128$ bytes on Apple Silicon). The CPU never fetches individual bytes; it fetches and writes back entire $L$-byte coherence lines.

\subsection{Coherence and False Sharing}

We use MESI terminology (Modified, Exclusive, Shared, Invalid)~\cite{mesi1984} as an explanatory model for cache-coherence traffic on common shared-memory multiprocessors. The implementation depends only on the general property that writes to a shared coherence granule require exclusive ownership and invalidate copies held by other cores; exact protocol states and instruction costs are microarchitecture-specific.

The critical consequence is \textbf{false sharing}~\cite{falsesharing1993}: if two independent variables, accessed concurrently by two different cores, reside on the same $L$-byte coherence line, a write by one core forces an ownership transfer on the other core's copy, even though the second core is accessing a logically unrelated variable. This is a pure hardware serialization artifact with no algorithmic solution other than spatial separation.

\subsection{Atomics and Memory Ordering Cost}

Atomic operations (\texttt{CAS}, fetch-and-add) on a shared memory location generally require exclusive ownership of the coherence line via an RFO transfer before executing the atomic read-modify-write. Under high concurrency, a single globally contested atomic (e.g., a global clock-hand pointer) causes every participating core to serialize on coherence round-trips~\cite{dice,amdahl1967}. The lock-free design methodology necessary to escape this bound is treated extensively by Herlihy and Shavit~\cite{lockfree2004}.

\subsection{Research Question and Contributions}
Set associativity, SWAR signatures, S3-FIFO queues, and stack-sharded counters are established systems building blocks; \texttt{liteLRU} contributes their lock-free, bit-parallel integration for managed runtimes. Specifically, we investigate whether a bounded-probe, 64-way set-associative cache using bit-sliced S3-FIFO state in 128-byte chunks, single-pointer immutable entries, and stack-sharded telemetry can simultaneously deliver lock-free throughput, scan resistance, and compact metadata in Go. Separating \textbf{Safety} (no torn payloads, invalid pointer exposure, unsynchronized mutation, or failed-read buffer corruption), \textbf{Progress} (lock-free bounded-probe reads and retry-bounded, best-effort writes), and \textbf{Performance}, we make four contributions:
\begin{itemize}
    \item \textbf{Bitmask S3-FIFO within 64-Way Chunks:} A lock-free S3-FIFO eviction engine (Small/Main partition mask \texttt{prob}, 2-bit bit-sliced saturating frequencies \texttt{f0}/\texttt{f1}, 128-bit resetting Ghost Bloom filter \texttt{ghost0}/\texttt{ghost1}, and dual 6-bit rotating hands \texttt{hand}/\texttt{handM}) packed alongside 64 byte signatures inside a single 128-byte off-heap \texttt{chunk} (2~B/slot), advancing via hardware \texttt{CTZ}.
    \item \textbf{Single-Pointer Immutable Entries (Seqlock Elimination):} Collapsing the earlier 128-byte padded per-slot seqlocks and 4-slice SoA arrays into one \texttt{entries []atomic.Pointer[cacheEntry]} array (8~B/slot) pointing to immutable 64-byte \texttt{cacheEntry} snapshots (10~B/slot total fixed metadata vs.\ 162~B/slot in v1 on ARM64), eliminating multi-array L1D misses, seqlock retries, failed-read \texttt{dst} mutation, and any 64-bit generation wraparound assumption.
    \item \textbf{Sub-Line Layout \& Stack-Sharded Telemetry:} Splitting read-mostly \texttt{sigs} $[0,64)$ from mutating control bitmasks $[64,128)$ inside every \texttt{chunk}, and sharding counters across 128 cache-line-padded \texttt{statStripe} slots indexed by 2~KB-aligned goroutine stack pointers (\texttt{sp >> 11}) rather than key hashes---preventing cross-core counter ping-pong on skewed hot keys.
    \item \textbf{Load-Shedding Best-Effort Admission Protocol:} A contention-bounded, non-linearizable write protocol capping per-claim ownership CAS retries on $W_k$ to $R=10$ attempts (with post-claim signature-word CAS retries scoped outside $R$).
\end{itemize}

The rest of this paper is structured as follows: Section~\ref{sec:hybrid} details the hybrid memory layout and SWAR filtering, Section~\ref{sec:related} discusses related work, Section~\ref{sec:soa} explains the control-plane vs.\ payload layout tradeoff, and the remaining sections analyze Bitmask S3-FIFO, correctness, coherence-line isolation, and evaluation.

\section{Hybrid Memory Architecture and GC Isolation}
\label{sec:hybrid}

Go's garbage collector is a concurrent tri-color mark-and-sweep~\cite{gogc2018}. An earlier \texttt{liteLRU} v1 prototype maintained off-heap \texttt{slotState} seqlocks (128~B/slot on ARM64) plus four separate heap \texttt{atomic.Pointer} arrays (\texttt{methods}, \texttt{paths}, \texttt{handlers}, \texttt{params} = 32~B/slot), bloating fixed metadata to 162~B/slot and requiring up to four wrapper allocations and dereferences per entry.

\texttt{liteLRU} v2 pairs compact off-heap control chunks (2~B/slot) with single-pointer immutable \texttt{cacheEntry} snapshots (8~B/slot array overhead) through three architectural choices:

\begin{enumerate}
    \item \textbf{64-Way Set Associativity over Hash Maps:} Prior open-addressed designs considered for \texttt{liteLRU} require tombstones or epoch reclamation to preserve concurrent probe sequences. \texttt{liteLRU} instead overwrites a victim in place within a fixed 64-slot bucket selected by \texttt{HashRoute(method, path) \& (numGroups - 1)} via zero-allocation 8B/4B string mixing (\texttt{mixString}).
    \item \textbf{SWAR Signature Scanning:} Before dereferencing heap \texttt{cacheEntry} pointers, each \texttt{chunk} starts (bytes $[0,64)$) with \texttt{[8]atomic.Uint64} \texttt{sigs}, packing 64 non-zero 8-bit signatures (\texttt{sig8 = uint8(hash >> 32)}, clamped from 0 to 1). SWAR arithmetic tests 8~byte signatures per machine word gated by \texttt{validBits}; a byte match ($\sim 1/255$ per valid slot, $\sim 3.1\%$ per 8-slot word) triggers one \texttt{atomic.Pointer[cacheEntry]} load and full \texttt{(method, path)} string comparison. False positives never yield incorrect responses.
    \item \textbf{Micro-Metadata Off-Heap vs.\ Immunized Payloads:} Each \texttt{chunk} occupies 128~bytes (\texttt{sigs} at $[0,64)$ and control masks + hands at $[64,128)$) inside page-aligned anonymous \texttt{mmap} memory, while \texttt{entries []atomic.Pointer[cacheEntry]} remains on the Go heap for safe GC tracing. Eliminating v1's 8.1~MiB of per-slot seqlocks leaves only 128~KiB of chunk control state at 65,536 slots, making Go runtime GC overhead near-minimal across pacing regimes (\S 9.12).
\end{enumerate}

\section{Related Work}
\label{sec:related}

Concurrent cache design spans two complementary axes: the eviction \textit{policy} governing hit rates, and the concurrent \textit{mechanism} governing synchronization cost. \texttt{liteLRU} v2 advances the mechanism axis---executing \textbf{both} lookup filtering and S3-FIFO state transitions via lock-free 64-bit bitmasks without locks, global hands, or background eviction threads.

\textbf{Concurrent CLOCK Mechanisms.} The closest published system to \texttt{liteLRU} is MemC3~\cite{memc3}, which introduced concurrent CLOCK with 1-bit recency tags and optimistic locking to remove mutexes from reads. Our v1 prototype adapted MemC3 to Go with off-heap seqlocks and bulk \texttt{CTZ} scans over 1-bit CLOCK masks, while v2 replaces seqlocks with single immutable \texttt{atomic.Pointer} snapshots and upgrades 1-bit CLOCK to multi-bit bit-sliced S3-FIFO inside the same 128-byte chunk.

\textbf{S3-FIFO \& Scan-Resistant Policies.} Policies such as CAR, CLOCK-Pro~\cite{clockpro2005}, S3-FIFO~\cite{s3fifo2023}, and SIEVE~\cite{sieve2024} prevent one-hit scans from flushing hot sets. Production S3-FIFO caches like \texttt{otter}~\cite{otter} use ring buffers, mutex-guarded eviction queues, striped read buffers, and background draining. \texttt{liteLRU} v2 realizes S3-FIFO natively inside lock-free per-chunk bitmasks (\texttt{prob}, \texttt{f0}, \texttt{f1}, \texttt{hand}, \texttt{handM}, \texttt{ghost0}/\texttt{ghost1}) advancing inline via hardware \texttt{CTZ}.

\textbf{Production Go Caches.} Existing Go caches like \texttt{freecache}, \texttt{bigcache}, and \texttt{ristretto} amortize eviction via sharding or background goroutines; \texttt{liteLRU} executes lock-free bounded-probe reads and retry-bounded ($R=10$) inline admissions.

\section{Control-Plane Bit-Slicing vs.\ Single-Pointer Snapshots}
\label{sec:soa}

\textit{Note on Set Associativity:} Software caches traditionally use open-addressed hash maps, whereas hardware L1/L2 caches use $N$-way set associativity. \texttt{liteLRU} applies hardware-style set associativity in software to eliminate global hash-table locking and tombstone chains entirely.

In our v1 prototype, we separated the four payload fields into four heap \texttt{atomic.Pointer} arrays (32~B/slot) protected by 128-byte padded \texttt{slotState} seqlocks (162~B/slot total on ARM64). Empirical ablation exposed a clear distinction between control-plane bit-slicing and payload SoA in Go:

\begin{lstlisting}[language=Go]
// v1 payload SoA (32 B/slot across 4 arrays + 128 B/slot seqlocks)
methods  []atomic.Pointer[string]
paths    []atomic.Pointer[string]
handlers []atomic.Pointer[HandlerFunc]
params   []atomic.Pointer[[]Param]

// v2 split: bit-sliced control plane off-heap (2 B/slot) + single-pointer snapshot (8 B/slot)
type cacheEntry struct { // 64 bytes immutable snapshot on Go heap
    method  string
    path    string
    handler HandlerFunc
    params  []Param
}
entries []atomic.Pointer[cacheEntry] // 8 pointers per 64B line, 16 per 128B line
\end{lstlisting}

Placing signatures and S3-FIFO recency/frequency state in off-heap \texttt{uint64} bitmasks gives $64\times$ packing so aging, promotion, and \texttt{CTZ} selection touch only a single 128-byte chunk. Conversely, collapsing the four payload wrappers into one immutable 64-byte \texttt{cacheEntry} behind \texttt{entries []atomic.Pointer[cacheEntry]} packs 8 slot pointers per 64B line (16 per 128B line), shrinks fixed per-slot arrays by $16.2\times$ (10~B/slot vs.\ 162~B/slot on ARM64), turns four heap allocations per insert into one \texttt{cacheEntry} allocation, and eliminates the \texttt{Get} seqlock retry loop altogether. For $n$ matching candidates in a chunk, v2 fetches $\lceil (a + n \cdot 8\text{ B}) / L \rceil$ lines from \texttt{entries} plus only the matching \texttt{cacheEntry}.

\section{Bitmask S3-FIFO: From One Bit to Bit-Sliced Chunk Queues}

\subsection{The Cost of Pointer-Based Queues}

Traditional LRU~\cite{lru1965} maintains doubly-linked lists requiring 8 pointer writes per promotion behind a mutex, while canonical S3-FIFO~\cite{s3fifo2023} maintains three concurrent queues (Small FIFO, Main FIFO, Ghost FIFO). Protecting linked structures with mutexes serializes accesses, and lock-free pointer queues require epoch-based reclamation or background drainer goroutines to reclaim removed nodes safely~\cite{lockfree2004}.

\subsection{Bit-Sliced S3-FIFO Inside 128-Byte Chunks}

In v1, each chunk used a single bit $A_k$ (1-bit CLOCK~\cite{clock1969}), which lacked scan resistance (0/256 retained in \S 9.11) and collapsed to 0.00\% on a 65-key cyclic loop. \texttt{liteLRU} v2 embeds an \textbf{S3-FIFO-inspired} replacement policy inside each 64-slot chunk's second 64~bytes ($[64,128)$) via orthogonal 64-bit masks and two 6-bit rotating hands (\texttt{hand}, \texttt{handM}) (while \texttt{NewLRUCacheWithPolicy} exposes \texttt{PolicyCLOCK}, \texttt{PolicyCLOCKPlus}, and \texttt{PolicyS3FIFO} on the identical engine):

\begin{itemize}
    \item $V_k \in \{0,1\}^{64}$ (\texttt{valid}): bit $i = 1$ iff slot $i$ holds a published entry.
    \item $P_k \in \{0,1\}^{64}$ (\texttt{prob}): bit $i = 1$ iff valid slot $i$ belongs to the Small probationary partition; $M_k = V_k \land \neg P_k$ is the Main protected partition. Rather than true linked FIFO queues, bit-sliced partitions approximate FIFO eviction via rotating \texttt{hand}/\texttt{handM} scans plus bulk frequency promotion.
    \item $(F_{1,k}, F_{0,k}) \in \{0,1\}^{64} \times \{0,1\}^{64}$ (\texttt{f1}, \texttt{f0}): 2-bit bit-sliced saturating frequency ($00 \to 01 \to 11$). Reads skip atomic writes when the target frequency bit is already set.
    \item $W_k \in \{0,1\}^{64}$ (\texttt{writing}): bit $i = 1$ iff a writer exclusively owns slot $i$.
    \item $(G_{0,k}, G_{1,k})$ (\texttt{ghost0}, \texttt{ghost1}): a \textbf{128-bit resetting Ghost Bloom filter} reset automatically when $\text{popcount}(\texttt{ghost0}) \ge 34$. Unlike canonical S3-FIFO's exact FIFO Ghost queue, this Bloom filter trades bounded false-positive promotions and periodic history resets for fixed 16-byte chunk storage and zero heap allocations.
    \item \texttt{hand}, \texttt{handM} $\in \{0 \dots 63\}$: rotating 6-bit offsets for Small and Main circular selection via hardware \texttt{CTZ}~\cite{inteltzcnt,armclz}.
\end{itemize}

Upon eviction (\texttt{findVictim(k)}, \texttt{smallTarget = 4}), v2 checks empty slots ($\neg V_k \land \neg W_k$) first, then promotes touched Small entries across all 64 slots in $\mathcal{O}(1)$ via \texttt{hitSmall = (prob \& valid) \& f0} (clearing \texttt{prob}, \texttt{f0}, and \texttt{f1} on promoted slots), evicts unhit Small slots if $\text{popcount}(\texttt{prob}) \ge 4$ (recording their hashes into \texttt{ghost0}/\texttt{ghost1}), or else scans/ages only Main entries via \texttt{handM}. Ghost hits on admission enter Main directly ($P_k[i]=0$); cold misses enter Small ($P_k[i]=1$). Unsuccessful CAS/aging iterations are capped at $R=10$, returning \texttt{0xFFFFFFFF} to shed load under single-chunk saturation.

\subsection{Eliminating Global Locks and Shared Hands}

Because \texttt{liteLRU} hashes each key to a fixed 64-slot chunk $k = h(r) \bmod N$, both lookup (\texttt{Get}) and eviction (\texttt{Add}/\texttt{findVictim}) operate strictly within chunk $k$, removing cross-chunk contention while exposing per-set pressure ($P_k > 1$, \S 9.11).

\section{Algorithm and Correctness}

\subsection{State Definitions and Layout}
\begin{itemize}
    \item \textbf{Global:} Power-of-two capacity $C \ge 64$, chunks $N = C/64$, and stack-sharded \texttt{stats [128]statStripe}.
    \item \textbf{Per-Chunk (off-heap \texttt{mmap}, 128~B):} Sub-line 0 $[0,64)$ holds \texttt{sigs [8]atomic.Uint64}; Sub-line 1 $[64,128)$ holds \texttt{valid}, \texttt{prob}, \texttt{f0}, \texttt{f1}, \texttt{writing}, \texttt{ghost0}, \texttt{ghost1}, \texttt{hand}, and \texttt{handM} (2~B/slot).
    \item \textbf{Per-Slot (Go heap, 8~B/slot):} \texttt{entries []atomic.Pointer[cacheEntry]}, where each 64-byte \texttt{cacheEntry} holds an immutable \texttt{(method, path, handler, params)} snapshot.
\end{itemize}

\subsection{API Semantics, State Machine, and Multi-Mask Invariants}
\textbf{Best-Effort, Non-Linearizable Cache Semantics and Option~A Candidate Filtering.} \texttt{Add} is a best-effort, non-linearizable cache insertion/update rather than a globally serialized upsert. Fast-path updates acquire $W_k[i]: 0 \to 1$ and store a new immutable \texttt{*cacheEntry} pointer (shedding redundant updates when $W_k[i]=1$). Concurrent cold misses on distinct $W_k$ bits can insert duplicate slots; \texttt{Get} returns the lowest-index match and never mutates caller buffer \texttt{dst} before full key verification succeeds, guaranteeing zero \texttt{dst} mutation on misses. Under our single-pass Option~A read contract, \texttt{Get} loads \texttt{validBits = chk.valid.Load()} \textit{once} at entry as an initial residency candidate filter without re-checking \texttt{chk.valid} after \texttt{entries[idx].Load()}; thus, during an overwrite on a previously valid bit, a reader may observe either \texttt{oldEntry} or \texttt{newEntry} right before \texttt{chk.valid.Or(mask)} finishes, and both remain memory-safe and untorn because every published \texttt{*cacheEntry} is immutable.

\textbf{Slot Publication, \texttt{Clear()}, and Relaxed Policy Mask Invariants.} On eviction/insert: acquire $W_k[i]: 0 \to 1$ in \texttt{findVictim}; clear $V_k[i]\leftarrow 0$; load \texttt{old} and store \texttt{entries[idx].Store(newEntry)}; CAS \texttt{sig8} into \texttt{chk.sigs}; run \texttt{onAdmit} (record unhit Small victim hashes into Ghost, set $P_k[i]$ via Ghost check, clear \texttt{f0}/\texttt{f1}); publish $V_k[i]\leftarrow 1$; and release $W_k[i]\leftarrow 0$. \texttt{Clear()} iterates chunks sequentially, acquires all 64 $W_k$ bits via \texttt{CompareAndSwap(0, \textasciicircum uint64(0))}, zeroes chunk masks/signatures and sets \texttt{entries[idx].Store(nil)}, then clears all 128 \texttt{statStripe} counters (\texttt{Clear()} is non-atomic across chunks and can starve under continuous writes). Crucially, concurrency safety cleanly separates \textbf{hard ownership invariants} ($W_k[i]$ serializes all writes to \texttt{entries[idx]} and \texttt{sigs[bit]}) from \textbf{relaxed bitwise policy hints} (\texttt{prob}, \texttt{f0}, \texttt{f1}, \texttt{ghost0}, \texttt{ghost1}): lock-free \texttt{promoteFreq} reads and multi-word bulk aging/promotion in \texttt{findVictimS3FIFO} can transiently produce $\texttt{prob} \land \neg \texttt{valid} \ne 0$ or lose an overlapping frequency increment between \texttt{prob.And(\textasciicircum hitSmall)} and \texttt{f0.And(\textasciicircum hitSmall)}, shifting only local eviction preference inside chunk $k$ without ever compromising slot ownership or pointer safety.

\subsection{Go Memory Model Safety}
Every \texttt{*cacheEntry} (including a fresh \texttt{[]Param} copy if non-empty) is fully initialized before single-word \texttt{atomic.Pointer.Store} publication and never mutated afterward~\cite{gomem2024}. Storing \texttt{entries[idx]} strictly precedes \texttt{chk.sigs} CAS and \texttt{chk.valid.Or}, so readers load complete immutable snapshots (including under Option~A candidate filtering) while all writers serialize on $W_k[i]$.

\subsection{Correctness Theorems}

\textbf{Theorem 1 (Bounded-Probe Lock-Free Reads).} \textit{Any thread executing \texttt{Get} terminates in a bounded number of metadata probes (at most 8 SWAR words and 64 slots; per-candidate key comparison cost is $\mathcal{O}(|\text{key}|)$), regardless of concurrent writers.}

\textit{Proof:} \texttt{Get} executes zero writer-wait or seqlock retry loops, checking \texttt{chk.valid}, at most 8 SWAR words, and matching candidate slots via \texttt{TrailingZeros64} with at most one \texttt{cacheEntry} load and key check per signature hit. $\square$

\textbf{Theorem 2 (Bounded Ownership-Claim Retries).} \textit{Any \texttt{Add} execution decomposes as $T_{\mathrm{Add}} = T_{\mathrm{lookup}} + T_{\mathrm{claim}} + T_{\mathrm{publication}}$, where ownership-claim CAS retries on $W_k$ satisfy $N_{\mathrm{claim,retries}} \le R = 10$ per matched fast-path slot and $N_{\mathrm{claim,retries}} \le R = 10$ inside \texttt{findVictim}, whereas post-claim signature-word publication ($T_{\mathrm{publication}}$) lies outside $R$. \texttt{Clear()} is blocking and non-atomic across chunks.}

\textit{Proof:} Both \texttt{findVictim} and per-matched-slot fast-path $W_k$ acquisition increment \texttt{retries} on every failed CAS/aging pass and exit once \texttt{retries >= 10}, leaving OS scheduling, \texttt{cacheEntry} allocation, duplicate scan length $d$, and post-claim \texttt{chk.sigs[bit/8].CompareAndSwap} retries outside $R$. $\square$

\textbf{Theorem 3 (Mutual Writer Exclusion, Immutable Snapshot Integrity \& Clean Misses).} \textit{No two writers may simultaneously mutate the same slot; every accepted read in \texttt{Get} observes a complete, untorn immutable snapshot without any 64-bit generation-wraparound assumption; and no miss mutates caller buffer \texttt{dst}.}

\textit{Proof:} Writer exclusion is enforced strictly by $W_k[i]$ ($0 \to 1$ CAS or all-ones CAS in \texttt{Clear()}). Under Option~A, \texttt{chk.valid.Load()} serves as an initial residency filter rather than a post-load barrier: sequential consistency of \texttt{entries[idx].Store} before \texttt{chk.sigs} CAS guarantees concurrent \texttt{entries[idx].Load()} returns either \texttt{nil} or a complete immutable \texttt{*cacheEntry} kept live by Go's GC. \texttt{Get} verifies full key equality before touching \texttt{dst[:len(ep.params)]}, leaving \texttt{dst} unmodified on misses and keeping relaxed policy-mask races confined to victim selection. $\square$

\section{Coherence-Line Layout and Stack-Sharded Telemetry}

Removing v1's 128-byte per-slot \texttt{slotState} seqlocks allows targeted coherence separation only where read/write traffic collides:
\begin{enumerate}
    \item \textbf{Sub-Line \texttt{chunk} Partitioning (128~B):} \texttt{TestLayoutInvariants} verifies $\text{sizeof}(\texttt{chunk})=128$, $\text{offsetof}(\texttt{sigs})=0$ (64~B), and $\text{offsetof}(\texttt{valid})=64$ (64~B). On x86\_64 ($L=64$), read-mostly \texttt{sigs} occupies a separate coherence line from mutating masks; on ARM64 ($L=128$), the entire 64-slot control plane fits in one line.
    \item \textbf{Stack-Sharded \texttt{statStripe} Telemetry:} Rather than v1's \texttt{hash \& 63} indexing (which caused all 8 cores hitting the same hot key to bounce a single counter cache line), v2's \texttt{workerStripe()} hashes the caller goroutine's 2~KB-aligned stack pointer (\texttt{sp >> 11}) across 128 $L$-byte-padded \texttt{statStripe} structs. We distinguish \textbf{counter-contention reduction} from collision-free identity: across concurrent parked goroutines (\texttt{TestWorkerStripeDistributionAndStackGrowth}), $G=8, 16, 32$ occupy 8/8, 16/16, and 29--32/32 distinct stripes across repeated runs, whereas $G=128$ yields 83--88/128 occupied stripes (max 4 per stripe) and $>24$~KiB stack growth relocates 16/16 workers across stripes while preserving exact \texttt{Stats()} totals (\texttt{hits=4000, misses=4000}). In \S 9.4, removing \texttt{statStripe} padding degrades uniform 80/20 throughput by \textbf{-15.4\%} (Regime~A1) while cache-density gains aid resident reads (+9.5\% in A0, +16.5\% in B).
\end{enumerate}

\section{Benchmark Methodology and Artifacts}

Standard Go micro-benchmarks use \texttt{b.RunParallel}, distributing $b.N$ iterations across goroutines via \texttt{pb.Next()}. While \texttt{b.RunParallel} amortizes synchronization over per-goroutine iteration batches rather than executing a shared atomic fetch-and-add on every call, it still adds harness overhead and reports only mean \texttt{ns/op} without latency percentiles. Running \texttt{BenchmarkParallelLRUCache} (\texttt{-count=5}) on \texttt{liteLRU} v2 (80\% \texttt{Get} / 20\% \texttt{Add}, 1024 capacity) yields medians of \textbf{44.04~ns/op} (1 core, range 42.51--44.75), \textbf{26.71~ns/op} (2 cores, range 24.97--34.92), \textbf{16.13~ns/op} (4 cores, range 15.69--19.08), and \textbf{17.88~ns/op} (8 cores, range 17.70--19.82, reflecting heterogeneous P/E-core scheduling across Apple M2's 4 performance + 4 efficiency cores), with \textbf{12 B/op} and \textbf{0 allocs/op} reported by \texttt{go test} (\texttt{Get} executes \texttt{0 B/op, 0 allocs/op}, while the 20\% \texttt{Add} mix averages $<0.5$ heap allocations per mixed op).

Our custom evaluation suite (\texttt{benchmarks/hardened\_eval/main.go}, 10 independent runs reporting median and interquartile range [IQR]) complements \texttt{b.RunParallel} by running independent worker loops over pre-allocated key arrays with no shared iteration counter and recording sampled or standalone latency percentiles directly.

\section{Discussion and Limitations}

\textbf{Best-Effort, Non-Linearizable Admission \& Stale Duplicate Resurrection.} Concurrent cold misses on the same key can place duplicates in distinct slots; \texttt{Get} returns the lowest-index match rather than necessarily the latest writer, updates target only that match, and extreme single-key contention sheds up to 80.90\% of redundant overwrites. \texttt{liteLRU} must be treated as a best-effort cache for immutable, idempotent, or staleness-tolerant workloads rather than a strictly serializable map.

\textbf{Blocking \texttt{Clear()} Under Continuous Writes.} Because \texttt{Clear()} polls per chunk for $W_k=0$, executes \texttt{CompareAndSwap(0, \textasciicircum uint64(0))}, and releases chunk 0 before locking chunk 1, \texttt{Clear()} is non-atomic across chunks and can starve under continuous concurrent writes.

\textbf{Memory Overhead (16.2$\times$ Reduction in Fixed Arrays).} Replacing 128-byte padded \texttt{slotState} seqlocks and 4 SoA pointer arrays with \texttt{entries []atomic.Pointer[cacheEntry]} (8~B/slot) plus 128-byte \texttt{chunk} metadata (2~B/slot) reduces fixed per-slot arrays on ARM64 ($L=128$) from 162~B/slot to \textbf{10~B/slot} (\textasciitilde 10~MB per million slots), plus one 64~B \texttt{cacheEntry} per populated slot (\textasciitilde 74~MB per million populated entries vs.\ \textasciitilde 120~MB for \texttt{otter}) and a fixed 16~KiB \texttt{[128]statStripe} array per cache.

\textbf{Set-Associative Capacity Boundaries vs.\ Global Policies.} Per-chunk Bitmask S3-FIFO (\texttt{smallTarget = 4}, $\sim 6.25\%$ probationary threshold plus 128-bit resetting Ghost Bloom filter) retains 256/256 hot keys under post-warmup sequential scans (\S 9.11), avoids 65-key cyclic collapse (96.83\% vs.\ 0.00\% under \texttt{CLOCK+}), and beats \texttt{otter} on Zipfian hit rates across all matched capacities (\S 9.6). Nevertheless, extreme hash skew landing $\gg 64$ hot keys into a single chunk ($H_k > 64$, e.g.\ 128 hot keys in one set) will evict entries locally even if sibling chunks are under-utilized.

\textbf{Fixed Capacity \& Scoped Bounds.} The cache does not resize and rounds capacity up to powers of two (\texttt{nextPowerOfTwo}, minimum 64). Ownership claim retries on $W_k$ are bounded by $R=10$; post-claim \texttt{chk.sigs} CAS lies outside $R$ (Theorem~2).

\textbf{Zero-Allocation Scope.} \texttt{Get} guarantees \textbf{0 heap allocations} (verified via \texttt{testing.AllocsPerRun}) and never mutates caller slice \texttt{dst} on misses, hitting 0~allocs whenever \texttt{cap(dst) >= len(params)}. \texttt{Add} allocates one immutable 64~B \texttt{cacheEntry} (plus fresh \texttt{[]Param} storage when non-empty) on publication.

\section{Conclusion}

We have presented the architecture and evaluation of \texttt{liteLRU} v2: compact off-heap \texttt{chunk} SWAR signatures and Bitmask S3-FIFO state (2~B/slot) paired with single-pointer immutable heap snapshots (\texttt{entries []atomic.Pointer[cacheEntry]}, 8~B/slot)~\cite{gogc2018,gomem2024}, hardware \texttt{CTZ} eviction without background threads~\cite{inteltzcnt,armclz}, stack-sharded $L$-byte-padded telemetry~\cite{falsesharing1993,mesi1984}, and $R=10$ bounded ownership claims. Across 10-run microbenchmark evaluations (\S\S~9.1--9.7, \S\S~9.11--9.12), \texttt{liteLRU} v2 outperforms \texttt{otter v1.2.4} on both read-dominated (128.59M vs.\ 113.74M ops/s, $1.13\times$ at $N=1\text{k}$, where \texttt{otter} edges hit rate 99.94\% vs.\ 99.19\%) and evicting (47.24M--56.29M vs.\ 9.12M--13.11M ops/s, $3.60\times\text{--}6.17\times$) workloads---including with an explicit 5~\textmu s miss penalty ($1.30\times$)---while retaining 256/256 warmed hot keys across sequential scans, beating or matching \texttt{otter} on Zipfian hit rates, and cutting uniform baseline sampled p99 latency to 500~ns (while matched-capacity loopback \texttt{net/http} throughput remains TCP/serialization bound at 76.4k--80.7k vs.\ 82.1k--82.9k~req/s).
