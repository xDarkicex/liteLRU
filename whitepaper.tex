\begin{abstract}
Concurrent approximate LRU structures often serialize cores on shared metadata. We investigate whether a bounded-probe, 64-way set-associative cache combining bit-parallel CLOCK recency tracking, padded seqlocks, and contention-aware admission load-shedding can deliver predictable concurrency costs without centralized locking in a garbage-collected runtime. We present \texttt{liteLRU}, a fixed-capacity cache in Go whose synchronization metadata (seqlocks, bitmasks, and SWAR signatures) resides in off-heap \texttt{mmap} memory while pointer-bearing payloads remain on the Go heap behind single-word \texttt{atomic.Pointer} wrappers to immutable values. Reads provide lock-free bounded-probe execution with zero heap allocations on hits when supplied a caller buffer; writes are retry-bounded, best-effort cache insertions/updates ($R=10$ retries) with non-linearizable concurrent key semantics. Across 10-run hardened evaluations on an 8-core Apple M2 (24 GB RAM), \texttt{liteLRU} sustains 20.89M--28.06M ops/s under 80/20 workloads ($1.36\times$ \texttt{otter v1.2.4} and $2.24\times$ \texttt{Mutex LRU} on the uniform baseline, with 875~ns sampled p99) and 19.14M--21.56M effective ops/s under write-heavy Zipf workloads while shedding 2.14--3.08\% of \texttt{Add} attempts (\S 9.1, \S 9.4, \S 9.7).
\end{abstract}

\section{Background: The Hardware Model}

To reason about concurrent cache design, we first establish a precise model of the hardware execution environment.

\subsection{The CPU Cache Hierarchy}

A modern multi-core processor maintains a private L1 cache (typically 32--64 KiB, 4--5 cycle latency), a private L2 cache (256 KiB -- 1 MiB, $\sim$12 cycle latency), and a shared L3 cache (several MiB, $\sim$40 cycle latency). Main memory sits at approximately 200--300 cycles. The performance implication is stark: a single L1 cache miss costs roughly $40\times$ more than an L1 hit.

The fundamental unit of coherency is the \textbf{cache line}, dependent on the target platform architecture (e.g., $L=64$ bytes on x86\_64, $L=128$ bytes on Apple Silicon). The CPU never fetches individual bytes; it fetches and writes back entire $L$-byte coherence lines.

\subsection{The MESI Coherency Protocol}

The MESI protocol (Modified, Exclusive, Shared, Invalid) was introduced by Papamarcos and Patel~\cite{mesi1984} to maintain coherency across private caches in a multi-processor system. The relevant state transitions are:

\begin{itemize}
    \item A line held in \textbf{Shared} state by multiple cores transitions to \textbf{Invalid} in all other cores when any single core writes to it.
    \item A write to an \textbf{Invalid} line requires a Read For Ownership (RFO)---a broadcast on the CPU interconnect requesting exclusive ownership from all other cores.
\end{itemize}

The critical consequence is \textbf{false sharing}~\cite{falsesharing1993}: if two independent variables, accessed concurrently by two different cores, reside on the same $L$-byte coherence line, a write by one core forces an RFO on the other core's copy, even though the second core is accessing a logically unrelated variable. This is a pure hardware serialization artifact with no algorithmic solution other than spatial separation.

\subsection{Atomics and Memory Ordering Cost}

Atomic operations (\texttt{CAS}, fetch-and-add) on a memory location whose cache line is not in the M (Modified) state require:
\begin{enumerate}
    \item An MESI state transition to Exclusive via RFO.
    \item The atomic read-modify-write in the modified cache line.
\end{enumerate}

Under high concurrency, a single globally contested atomic (e.g., a global clock-hand pointer) causes every participating core to serialize on RFO round-trips. As core count $N$ grows, the wait time for the contested line degrades superlinearly due to RFO round-trip amplification~\cite{dice}, a fact formalized by Amdahl~\cite{amdahl1967}. The lock-free design methodology necessary to escape this bound is treated extensively by Herlihy and Shavit~\cite{lockfree2004}.

\subsection{Research Question and Contributions}
CLOCK, set associativity, compact signatures, and seqlocks are well-established primitives; \texttt{liteLRU} does not propose a new eviction policy. Instead, we investigate whether a bounded-probe, 64-way set-associative cache using bit-parallel recency tracking, padded seqlocks, and contention-aware admission can provide predictable concurrency costs without centralized locking in a garbage-collected runtime. Separating \textbf{Safety}, \textbf{Progress} (lock-free bounded-probe reads and retry-bounded, best-effort writes), and \textbf{Performance}, we make the following contributions:
\begin{itemize}
    \item \textbf{Contention-Bounded Set-Associative Mechanism:} A 64-way set associative architecture utilizing chunked bitmasks and hardware \texttt{CTZ}, eliminating global clock hands and open-addressed tombstone maintenance.
    \item \textbf{Hybrid Memory Architecture:} Off-heap \texttt{mmap} allocation for pointer-free lock-free synchronization state (bitmasks, signatures, seqlocks) combined with on-heap \texttt{atomic.Pointer} SoA arrays to immutable values so the Go GC safely traces live strings, closures, and parameter slices.
    \item \textbf{Padded Seqlocks:} A cache-line-aligned structural layout using monotonic 64-bit seqlocks that yields lock-free bounded-probe reads and eliminates false sharing across per-slot \texttt{slotState} sequence counters (and per-stripe \texttt{statStripe} counters).
    \item \textbf{Load-Shedding Best-Effort Admission Protocol:} A contention-bounded, non-linearizable write protocol that caps per-admission claim retries to $R=10$ CAS attempts; under sustained contention, admission or redundant updates may be dropped rather than spinning unboundedly.
\end{itemize}

The rest of this paper is structured as follows: Section~\ref{sec:hybrid} details the hybrid memory architecture and 64-way set-associative SWAR design, Section~\ref{sec:related} discusses related work, Section~\ref{sec:soa} motivates the Structure-of-Arrays layout, and the remaining sections analyze the eviction algorithm, safety, and performance.

\section{Hybrid Memory Architecture and 64-Way Set Associative SWAR}
\label{sec:hybrid}

Go's garbage collector (GC) is a concurrent tri-color mark-and-sweep~\cite{gogc2018}. It introduces three categories of tail-latency interference directly relevant to a cache implementation:

\begin{itemize}
    \item \textbf{Write Barrier Overhead.} The GC requires write barriers on every pointer store to maintain the tri-color invariant. For a structure that stores handler function pointers or string headers, every \texttt{Add} operation incurs GC bookkeeping cost proportional to the number of pointer-typed fields written.
    \item \textbf{Stop-the-World Pauses.} While modern Go GC pause times are sub-millisecond, they are non-zero and non-deterministic. For a component targeting p99.9 tail latency in the low-microsecond range, any unpredictable pause invalidates latency guarantees.
    \item \textbf{Mark-Phase Heap Pressure.} A cache holding thousands of string values generates a large root set for the GC to scan during the mark phase, increasing mark duration proportionally with capacity.
\end{itemize}

\texttt{liteLRU} addresses this through two non-trivial architectural changes:

\begin{enumerate}
    \item \textbf{64-Way Set Associativity over Hash Maps:} The prior open-addressed designs considered by \texttt{liteLRU} use tombstones or comparable reclamation mechanisms to preserve concurrent probe sequences. Their maintenance and reclamation costs complicate predictable deletion behavior under sustained eviction. \texttt{liteLRU} instead overwrites a victim in place within a fixed set. An incoming route hash is mathematically mapped to a specific 64-slot bucket (a "set"). 
    \item \textbf{SWAR Signature Scanning:} To filter candidate slots within a 64-slot set before dereferencing heap pointers, \texttt{liteLRU} maintains a \texttt{uint64} signature word per 8 slots. Each byte in the word stores an 8-bit hash signature. SWAR-style scalar bitwise operations test eight 8-bit signatures per machine word, reducing pointer dereferences and branchy per-slot comparisons before full-key verification. Lookups are bounded by fixed 64-way associativity. Each SWAR byte match is verified with a full string comparison; false positives incur extra key comparisons across colliding slots, never an incorrect response. The signature array occupies 64 bytes. Because Go does not expose struct alignment primitives, the array may straddle two coherence lines, requiring at most two $L$-byte cache-line fetches. Evictions are restricted to the local 64-slot set, overwriting pointers in place and eliminating tombstones entirely.
\end{enumerate}

\section{Related Work}
\label{sec:related}

The problem of concurrent cache design generally branches into two orthogonal domains: optimizing the eviction \textit{policy} for higher hit rates, and optimizing the concurrent \textit{mechanism} for lower CPU overhead. \texttt{liteLRU} is strictly a contribution to the latter.

\textbf{Concurrent CLOCK Mechanisms.} The closest published system to \texttt{liteLRU} is MemC3~\cite{memc3}, which optimized Memcached by introducing a concurrent CLOCK with 1-bit recency tags and optimistic locking to remove mutexes from the read path. \texttt{liteLRU} builds on this foundation by applying it to the Go runtime (off-heap mmap, zero-allocation SoA), but replaces MemC3's sequential bit-checks with bulk 64-bit bitmask evaluations via hardware \texttt{CTZ} intrinsics, drastically reducing eviction scan latency.

\textbf{Advanced Eviction Policies.} Recent systems like CAR, CLOCK-Pro~\cite{clockpro2005}, S3-FIFO~\cite{s3fifo2023}, and SIEVE~\cite{sieve2024} demonstrate that scan-resistant or frequency-aware eviction policies outperform 1-bit CLOCK~\cite{clock1969} on web workloads. These policy innovations are largely orthogonal to the mechanism: a SIEVE or S3-FIFO algorithm still requires a concurrent implementation strategy to scale across cores without locking.

\textbf{Production Go Caches.} Existing Go caches like \texttt{freecache}, \texttt{bigcache}, and \texttt{ristretto} achieve high throughput via sharding and background eviction goroutines. \texttt{liteLRU} takes a different approach: rather than amortizing eviction cost over background threads or coarse-grained shard locks, \texttt{liteLRU} eliminates the locking overhead on lookups via bitmask mathematics and seqlocks, enabling lock-free bounded-probe reads with retry-bounded, best-effort writes.

\section{Why Structure of Arrays over Array of Structs}
\label{sec:soa}

\textit{Note on Set Associativity:} Software caches traditionally use open-addressed hash maps, whereas hardware L1/L2 caches use $N$-way set associativity. \texttt{liteLRU} applies this hardware-style set associative design in software to bypass the global locking overhead of hash maps entirely.


The conventional cache entry is represented as an Array of Structs (AoS):

\begin{lstlisting}[language=Go]
// AoS: one struct per entry
type Entry struct {
    method  string     // 16 bytes (ptr + len)
    path    string     // 16 bytes
    handler uintptr    // 8 bytes
    params  []Param    // 24 bytes
}
// In memory: [entry0 | entry1 | entry2 | ...]
\end{lstlisting}

Consider a \texttt{Get} operation that must validate $n$ candidate entries by comparing their \texttt{method} and \texttt{path} fields. In AoS, each entry occupies $\sim$64+ bytes. Accessing the \texttt{method} field of entry $i$ and entry $i+1$ requires fetching two separate $L$-byte cache lines. For $n$ entries, the cache-line cost is $n$ fetches just for a single field.

The Structure of Arrays (SoA) alternative, widely employed in high-performance and SIMD-oriented computing~\cite{soasimd2009}, separates fields into parallel arrays:

\begin{lstlisting}[language=Go]
// SoA: one array per field
methods  []string    // [m0, m1, m2, ...] -- contiguous
paths    []string    // [p0, p1, p2, ...] -- contiguous
handlers []uintptr   // [h0, h1, h2, ...] -- contiguous
\end{lstlisting}

When a \texttt{Get} operation scans \texttt{methods[i]} and \texttt{methods[i+1]}, both values reside in the same $L$-byte cache line (a \texttt{string} header is 16 bytes, placing 4 per cache line). Accessing 4 consecutive methods costs 1 cache-line fetch instead of 4 (since the target coherence-line size $L$ is at least 64 bytes).

Formally, let $W_f$ be the width of field $f$ and $L$ be the target platform's coherence-line size. For AoS, the number of cache lines fetched to access field $f$ across $n$ consecutive entries depends heavily on padding and struct size. If $\text{sizeof}(\text{Entry}) \le L$ and the compiler naturally packs them, we approximate the cost as fetching one new cache line per entry:

\begin{equation}
\text{Lines}_{AoS}(n, f) \approx n
\end{equation}

For SoA, values are packed contiguously. Accounting for an arbitrary unaligned start offset $a$ within a coherence line ($0 \le a < L$):

\begin{equation}
\text{Lines}_{SoA}(n, f) = \left\lceil \frac{a + n \cdot W_f}{L} \right\rceil
\end{equation}

Since $W_f \ll \text{sizeof}(\text{Entry})$ for any individual field, we have $\text{Lines}_{SoA}(n, f) \ll \text{Lines}_{AoS}(n, f)$ for sufficiently large $n > 1$.

\section{Why Bitsets for Recency Tracking}

\subsection{The Cost of Pointer-Based Recency}

Traditional LRU~\cite{lru1965} tracks recency by maintaining a doubly-linked list ordered from Most Recently Used (MRU) to Least Recently Used (LRU). A cache hit requires:
\begin{enumerate}
    \item Unlinking the accessed node from its current position: 4 pointer writes.
    \item Relinking it at the MRU head: 4 pointer writes.
\end{enumerate}

Each of these pointer writes on a concurrent system must be protected by a mutual exclusion lock, serializing all \texttt{Get} operations system-wide. Lock-free linked-list variants exist but require hazard pointers or epoch-based reclamation to prevent use-after-free races~\cite{lockfree2004}, reintroducing serialization on shared epoch counters.

\subsection{CLOCK as an Approximation}

The foundational CLOCK algorithm~\cite{clock1969} approximates LRU by abandoning exact recency ordering (later extended by scan-resistant designs such as CLOCK-Pro~\cite{clockpro2005}). Instead of tracking \textit{which} entry is least recently used, 1-bit CLOCK tracks \textit{whether} each entry has been accessed since the last eviction sweep---a single bit per entry.

\begin{itemize}
    \item Upon \texttt{Get}: the entry's reference bit is set to 1 via an atomic OR.
    \item Upon eviction: a hand sweeps the array. Reference bit 1 is cleared to 0 (second chance). Reference bit 0 designates the eviction victim.
\end{itemize}

This approximates LRU behavior without pointer manipulation, requiring only non-blocking atomic bitwise operations. Recent research such as S3-FIFO~\cite{s3fifo2023} and SIEVE~\cite{sieve2024} further refines the eviction policy. However, these works do not address the parallel execution cost of the eviction mechanism itself, which is the problem we solve.

\subsection{From One Bit to One 64-bit Integer}

Standard CLOCK still maintains a global clock-hand pointer---an atomic integer indicating the current sweep position. Every eviction increments this counter and examines a single entry. Under high concurrency, all evicting threads contend on this single atomic, creating repeated coherence ownership transfers under contention.

The key observation: if we partition the cache into chunks of exactly 64 entries, the valid state and access state of all 64 entries in a chunk fit into two 64-bit integers:

\begin{itemize}
    \item $V_k \in \{0,1\}^{64}$: bit $i = 1$ iff slot $i$ holds a valid entry.
    \item $A_k \in \{0,1\}^{64}$: bit $i = 1$ iff slot $i$ has been accessed since the last sweep.
    \item $W_k \in \{0,1\}^{64}$: bit $i = 1$ iff a writer currently owns slot $i$ for mutation.
\end{itemize}

A slot is an eviction candidate if it is empty ($V_k[i] = 0$) or valid but unaccessed ($V_k[i] = 1 \land A_k[i] = 0$), provided it is not currently owned by a writer ($W_k[i] = 0$). The complete candidate set across all 64 slots is computed in a single bitwise expression:

\begin{equation}
C_k = \neg (V_k \land A_k) \land \neg W_k
\end{equation}

The index of the first candidate is extracted using the hardware Count Trailing Zeros (CTZ) instruction~\cite{inteltzcnt,armclz}. It is crucial to handle platform-specific zero behavior: on x86\_64, \texttt{TZCNT} returns 64 when the input is zero, whereas on ARM64, \texttt{RBIT} + \texttt{CLZ} requires an explicit branch or zero-check. When a non-zero candidate mask exists:

\begin{equation}
i^* = \text{CTZ}(C_k)
\end{equation}

This replaces an $\mathcal{O}(N)$ sequential scan over $N$ atomic loads with two register-width bitwise operations and one hardware intrinsic, bounding eviction search to a strict hardware-constant time within any chunk.

If $C_k = 0$, it indicates either all valid slots in the current chunk have been recently accessed or free candidates are currently locked in $W_k$. The algorithm clears valid access bits via \texttt{chk.accessed.And(\textasciicircum validBits)} and retries up to $R=10$ iterations. We explicitly distinguish \textbf{CLOCK recency imprecision} from \textbf{ownership safety}: stale $A_k$ observations and bulk clearing affect only approximate victim preference, whereas exclusive slot ownership is enforced strictly by the $W_k[i]$ CAS ($0 \to 1$) before $V_k[i]$ or slot contents are mutated.

\textbf{Writer Progress and Claim Protocol.}

The eviction search process executes as follows:
\begin{enumerate}
    \item Extract candidate index $i = \text{CTZ}(C_k)$.
    \item Execute an atomic Compare-And-Swap (CAS) to set $W_k[i] \leftarrow 1$.
    \item If the CAS fails (another writer claimed it), restart at step 1 for the same chunk.
    \item If $W_k[i] = 1$ is successfully claimed, proceed to step 1 of the concurrent Set Associative Write Consistency protocol defined in \S 6.
\end{enumerate}

To guarantee contention-bounded admission and bound the worst-case scenario where a chunk is pathologically saturated by concurrent writers (e.g., a Thundering Herd), \texttt{liteLRU} employs \textbf{Load-Shedding Eviction}. The \texttt{findVictim} loop attempts to claim a write-lock (\texttt{writing} bit) on an eviction candidate. If it fails to claim any slot after 10 retries, it returns a sentinel failure value (\texttt{0xFFFFFFFF}). The \texttt{Add} operation intercepts this sentinel and safely drops the cache admission. By sacrificing absolute admission under extreme contention, \texttt{liteLRU} bounds write-side work to a fixed number of CAS attempts; under sustained contention, admission may be dropped.

\subsection{Eliminating the Global Clock Hand}

Because \texttt{liteLRU} seeds the starting chunk index from the hash of the incoming route, $k_\text{start} = h(r) \bmod N$, there is no shared global clock-hand atomic. Each writer begins its eviction sweep at a deterministic but distributed starting position, naturally load-balancing eviction pressure across chunks without any coordination. 

\section{Algorithm and Correctness}

\subsection{State Definitions and Layout}
The cache state is divided into global configuration, per-chunk metadata, and per-slot data:
\begin{itemize}
    \item \textbf{Global:} Total capacity $C$ and number of chunks $N = C/64$.
    \item \textbf{Per-Chunk (off-heap \texttt{mmap}):} A \texttt{chunk} struct containing 64-bit masks $V_k$ (valid bits), $W_k$ (writing/ownership bits), $A_k$ (access/recency bits), and an array of 8 \texttt{uint64} SWAR signatures for fast scanning.
    \item \textbf{Per-Slot:} A \texttt{slotState} (off-heap \texttt{mmap}, padded to the target platform's $L$-byte coherence stride) containing the monotonic 64-bit seqlock $S_i$, alongside Structure of Arrays (SoA) slices on the Go heap (\texttt{[]atomic.Pointer[string]}, \texttt{[]atomic.Pointer[HandlerFunc]}, \texttt{[]atomic.Pointer[[]Param]}) pointing to immutable key and payload objects.
\end{itemize}

\subsection{API Semantics, State Machine, and Control Flow}
\textbf{Best-Effort, Non-Linearizable Cache Semantics and Duplicate Keys.} \texttt{Add(key, value)} is a best-effort, non-linearizable cache insertion/update rather than a globally serialized upsert. If an existing valid entry for \texttt{key} is matched during the chunk scan, \texttt{Add} acquires exclusive slot ownership via $W_k[i]$ and updates the value in place under the seqlock; if $W_k[i]$ is already owned by another writer for that exact slot, \texttt{Add} sheds the redundant concurrent update. If no matching entry is found, \texttt{Add} claims a victim slot via \texttt{findVictim(k)}. Under simultaneous cold-start misses on the same key, two writers holding distinct $W_k$ bits can both insert into separate slots (e.g., Writer A in slot 4 with $v_A$, Writer B completing later in slot 12 with $v_B$). Because \texttt{Get} scans slots $0\dots 63$ in ascending order and sets $A_k$ only on the first clean match, \texttt{Get} returns $v_A$ from slot 4 even though Writer B completed later, and future fast-path updates target only slot 4. If slot 4 is subsequently evicted, the older duplicate in slot 12 can resurface (\textbf{stale duplicate resurrection}) until reclaimed by CLOCK sweeps. Callers requiring strict coherent per-key updates over mutable state must serialize writes externally.

\textbf{Slot Publication State Machine.} Each slot transitions through \textbf{INVALID} ($V_k[i]=0$), \textbf{WRITING} ($W_k[i]=1, S_i \equiv 1 \pmod 2$), and \textbf{VALID} ($V_k[i]=1, S_i \equiv 0 \pmod 2$). \texttt{Clear()} acquires all 64 $W_k$ bits atomically via \texttt{CompareAndSwap(0, \textasciicircum uint64(0))} (retrying on failure after \texttt{w == 0}), clears $V_k/A_k/\text{sigs}$, and advances $S_i$ monotonically ($S_i+1 \to S_i+2$) rather than resetting to zero.

\textbf{Get(key)}
\begin{enumerate}
    \item Hash the key to find chunk $k$, stripe index \texttt{hash \& 63}, and 8-bit signature \texttt{sig8}.
    \item Scan the 8 SWAR signature words using byte-wise comparison.
    \item For any candidate slot $i$ in ascending slot order, check $V_k[i]=1$.
    \item Load $S_{i, \text{start}}$. If odd, skip slot (active write).
    \item Perform full-key equality verification (\texttt{slotKeyMatches}) by loading \texttt{atomic.Pointer[string]} key fields (\texttt{methods[i]}, \texttt{paths[i]}) and comparing strings; if unequal, skip slot.
    \item Load the single-word \texttt{atomic.Pointer} value pointers (\texttt{handlers[i]}, \texttt{params[i]}) and copy any \texttt{[]Param} into caller buffer \texttt{dst}.
    \item Load $S_{i, \text{end}}$. If $S_{i, \text{start}} \neq S_{i, \text{end}}$, skip slot (concurrent write).
    \item Check $A_k[i]$ and only if $A_k[i]=0$, atomically OR bit $i$ into $A_k$; increment hit counter and return.
    \item If no slot matches cleanly, increment miss counter and return miss.
\end{enumerate}

\textbf{Add(key, value)}
\begin{enumerate}
    \item Hash the key to find chunk $k$ and \texttt{sig8}.
    \item \textbf{Fast-path update:} Scan the 8 SWAR words for a valid matching slot bracketed by matching even seqlock reads ($S_{i,\text{start}} = S_{i,\text{end}}$). Claim $W_k[i]: 0 \to 1$ via CAS (retrying up to $R=10$ times on unrelated-slot $W_k$ interference; dropping if $W_k[i]=1$). Re-validate $(V_k[i]=1 \land \text{key matches})$ under $W_k[i]=1$. Advance $S_i \to S_i+1$, publish immutable value pointers, set $A_k[i]\leftarrow 1$ if unset, advance $S_i \to S_i+2$, release $W_k[i]\leftarrow 0$, and return.
    \item \textbf{Eviction / admission:} Otherwise run \texttt{findVictim(k)}. If it returns \texttt{0xFFFFFFFF}, increment drops and return.
    \item Clear $V_k[i] \leftarrow 0$ and store $S_i \leftarrow S_i + 1$ (odd).
    \item Publish immutable \texttt{atomic.Pointer} key and value fields.
    \item Update the SWAR signature byte via CAS, and set $A_k[i] \leftarrow 1$ (second-chance protection).
    \item Close generation ($S_i \leftarrow S_i + 2$, even), publish $V_k[i] \leftarrow 1$ (visibility linearization point), and release $W_k[i] \leftarrow 0$.
\end{enumerate}

\textbf{findVictim(chunk k)}
\begin{enumerate}
    \item Retry loop bounded by $R=10$ failed iterations (\texttt{retries < 10}).
    \item Load $V_k, A_k, W_k$ and compute $C_k = \neg(V_k \land A_k) \land \neg W_k$.
    \item If $C_k \neq 0$, pick $i = \text{CTZ}(C_k)$ and attempt CAS $W_k[i]: 0 \to 1$ (ownership linearization point). Return slot $i$ on success; otherwise increment \texttt{retries}.
    \item If $C_k = 0$, atomically clear valid access bits via \texttt{chk.accessed.And(\textasciicircum validBits)}, increment \texttt{retries}, yield via \texttt{runtime.Gosched()} if $W_k \neq 0$, and loop while \texttt{retries < 10}.
    \item If 10 retries are exhausted, return \texttt{0xFFFFFFFF}.
\end{enumerate}

\textbf{Clear()}
\begin{enumerate}
    \item Iterate sequentially over chunks $k = 0 \dots N-1$.
    \item Loop loading $w = W_k$: if $w \neq 0$, yield via \texttt{runtime.Gosched()} and retry; once $w=0$, execute atomic \texttt{CompareAndSwap(W\_k, 0, \textasciicircum uint64(0))} (retrying from step 2 if a racing writer acquires a bit before CAS completes).
    \item Clear $V_k \leftarrow 0$, $A_k \leftarrow 0$, and all 8 SWAR \texttt{sigs} words.
    \item Advance every slot $S_i \to S_i+1 \to S_i+2$ while storing \texttt{nil} into its four \texttt{atomic.Pointer} slices, release $W_k \leftarrow 0$, and finally zero all 64 \texttt{statStripe} counters.
\end{enumerate}
\textit{Progress Note on \texttt{Clear()}:} \texttt{Clear()} is blocking and not starvation-free under continuous concurrent writes; callers requiring deterministic completion under write load must externally quiesce writers.

\textbf{Linearization Points and Stale Mask Snapshots.} Stale $A_k$ reads prior to the $W_k$ CAS affect only approximate CLOCK victim preference, whereas exclusive slot ownership is linearized solely at the successful $W_k$ CAS. Once $W_k[i]=1$ is held, no other writer or \texttt{Clear()} can mutate slot $i$, $V_k[i]$, or $S_i$ until $W_k[i]$ is released.

\subsection{Go Memory Model Safety}

Seqlock validation alone does not prevent multi-word struct tearing (e.g., 16-byte \texttt{string} or 24-byte \texttt{[]Param} headers) or Go data races if slice backing arrays are mutated in place before $S_{i,\text{end}}$ is checked. \texttt{liteLRU} therefore pairs off-heap synchronization metadata with single-word \texttt{atomic.Pointer} publication of immutable heap objects (\texttt{string}, \texttt{HandlerFunc}, freshly copied \texttt{[]Param}). All writers (\texttt{Add} fast path, \texttt{Add} eviction, and \texttt{Clear}) serialize per slot via $W_k[i]$, $S_i$ is a monotonic \texttt{atomic.Uint64} padded to $L$ bytes, and all synchronization relies on Go's sequentially consistent \texttt{sync/atomic} total order~\cite{gomem2024}.

\subsection{Correctness Theorems}

\textbf{Theorem 1 (Bounded-Probe Lock-Free Reads).} \textit{Any thread executing \texttt{Get} terminates in a bounded number of metadata probes (at most 8 SWAR words and 64 slots; per-candidate key comparison cost is $\mathcal{O}(|\text{key}|)$), regardless of the state or execution speed of concurrent writers.}

\textit{Proof:} \texttt{Get} contains no unbounded loops and never retries on seqlock conflict. It evaluates at most 8 SWAR words and 64 slot indices; for each matching byte it executes bounded atomic loads ($V_k$, $S_{i,\text{start}}$, single-word \texttt{atomic.Pointer} key/value pointers, $S_{i,\text{end}}$) and at most one full-key comparison before returning hit (with one optional atomic \texttt{Or} on $A_k$) or advancing to miss. $\square$

\textbf{Theorem 2 (Bounded Admission Attempt Complexity).} \textit{Any thread executing \texttt{Add} performs at most $R=10$ claim retries in \texttt{findVictim} (and at most $R=10$ $W_k$-claim retries per matched fast-path slot), bounding admission-attempt work as $T_{\mathrm{admission}} \le R \cdot T_{\mathrm{attempt}} + T_{\mathrm{publication}}$. Unlike \texttt{Get} and \texttt{Add}, \texttt{Clear()} is blocking and requires quiescent or bounded writer overlap on $W_k$ to terminate.}

\textit{Proof:} In \texttt{findVictim}, every failed $W_k$ CAS and every $A_k$-clearing pass increments the same \texttt{retries} counter, returning \texttt{0xFFFFFFFF} once \texttt{retries >= 10} ($N_{\mathrm{CAS,claim}} \le R = 10$). The fast-path $W_k[i]$ claim loop likewise caps retries at $R=10$ on unrelated-slot interference and drops immediately if $W_k[i]=1$. This bounds admission-attempt retry work rather than deterministic wall-clock latency (scheduling, allocation, and post-claim CAS updates to \texttt{sigs} lie outside $R$). \texttt{Clear()} instead retries its \texttt{w == 0} check and \texttt{CompareAndSwap(0, \textasciicircum uint64(0))} until acquiring the chunk. $\square$

\textbf{Theorem 3 (Safety Invariant).} \textit{Assuming fewer than $2^{63}$ complete write generations occur to a single slot during one active \texttt{Get} probe (precluding 64-bit counter wraparound between $S_{i,\text{start}}$ and $S_{i,\text{end}}$), no two writers may simultaneously mutate the same slot, and an accepted read in \texttt{Get} observes a complete, untorn key/value snapshot from a single publication generation.}

\textit{Proof:} Mutual exclusion across all writers (\texttt{Add} fast path, \texttt{Add} eviction, and \texttt{Clear}) is enforced by $W_k[i]$ (acquired atomically via $W_k[i]:0\to 1$ CAS or all-ones \texttt{CompareAndSwap} in \texttt{Clear}). Under Go's sequentially consistent atomic order, writer generation $g$ stores all immutable \texttt{atomic.Pointer} fields while $S_i = 2g+1$ (odd), then stores $S_i \leftarrow 2g+2$ (even) before setting $V_k[i] \leftarrow 1$. Under the bounded-generation hypothesis ($<2^{63}$ complete writes during a single probe), observing $S_{i,\text{start}} = S_{i,\text{end}} = 2g+2$ brackets all \texttt{slotKeyMatches} and value pointer loads strictly within generation $2g+2$. Because every published target object is immutable after publication, the reader cannot observe torn headers or concurrent backing-array mutations. $\square$

\section{Cache-Line Padding to Eliminate False Sharing}

A naive implementation allocates seqlocks as a contiguous slice \texttt{[]atomic.Uint32}. Each \texttt{uint32} is 4 bytes, placing multiple seqlocks per cache line. By the MESI coherency protocol~\cite{mesi1984}, a write to slot $j$ invalidates the cache line holding multiple adjacent seqlocks across all other cores, inducing spurious RFOs even for logically independent operations. This is the false sharing pathology described by Bolosky and Scott~\cite{falsesharing1993}.

\texttt{slotState} metadata is allocated in a page-aligned anonymous \texttt{mmap} region. For each supported platform, \texttt{liteLRU} selects a slot stride equal to the platform's verified coherence-line size $L$ (64 bytes for x86\_64, 128 bytes for Apple Silicon). Because the mapping base is page-aligned and each slot has stride $L$, distinct slot states begin on distinct coherence-line boundaries.

\textbf{Theorem (Cache Line Isolation).} \textit{On a platform with coherence-line size $L$, if the base of the slot-state region is aligned to $L$ and each slot state has stride $L$, distinct slots occupy distinct coherence lines.}

\textit{Proof.} Let $\text{addr}(S_i)$ denote the base address of the padded slot state for slot $i$. We define:

\begin{lstlisting}[language=Go]
// L is the verified coherence-line size for the target platform via build tags.
type slotState struct {
    seq atomic.Uint64 // 8 bytes
    _   [L - 8]byte   // L-8 bytes padding
}
\end{lstlisting}

Because the \texttt{mmap} allocation guarantees $\text{addr}(S_0) \pmod L = 0$ (page alignment implies $L$ alignment for $L \le 4096$), and $\text{addr}(S_{i+1}) = \text{addr}(S_i) + L$, adjacent \texttt{slotState} entries reside on disjoint, non-overlapping $L$-byte aligned cache lines. A write to $S_i$ can require coherence activity for its own line but does not require ownership transfer for a distinct \texttt{slotState} line. $\square$

We explicitly clarify the \textbf{scope of padding isolation}: $L$-byte padding isolates distinct \texttt{slotState} sequence counters and distinct \texttt{statStripe} stats structs onto separate coherence lines. By contrast, all 64 slots belonging to the same chunk $k$ intentionally share the chunk's compact \texttt{uint64} bitmasks ($V_k$, $A_k$, $W_k$) and 8-word \texttt{sigs} array. Packing 64 slots into one \texttt{uint64} reduces metadata word count by $64\times$ compared to per-slot flags, trading intrachunk mask sharing for constant-width \texttt{CTZ} victim selection. \texttt{liteLRU} mitigates this concentration by checking \texttt{chk.accessed} before issuing an atomic \texttt{Or} on \texttt{Get} and bounding retry loops on shared chunk words to $R=10$. Similarly, sharded statistics use 64 padded \texttt{statStripe} structs indexed via \texttt{hash \& 63}, distributing---rather than eliminating---counter contention.

\section{Benchmark Methodology and Artifacts}

Standard Go micro-benchmarks use \texttt{b.RunParallel}, distributing $b.N$ iterations across goroutines via \texttt{pb.Next()}. \section{Discussion and Limitations}

\textbf{Best-Effort, Non-Linearizable Admission \& Stale Duplicate Resurrection.} Concurrent cold misses on the same key can place duplicates in distinct slots; \texttt{Get} returns the lowest-index match rather than necessarily the latest writer, and updates mutate only the lowest-index match, so evicting it can briefly resurrect an older duplicate at a higher index until CLOCK reclaims it. Callers requiring linearizable upserts must serialize writes externally.

\textbf{Blocking \texttt{Clear()} Under Continuous Writes.} Because \texttt{Clear()} polls for $W_k=0$ and executes \texttt{CompareAndSwap(0, \textasciicircum uint64(0))}, continuous concurrent writes can starve \texttt{Clear()}; callers needing deterministic teardown must externally quiesce writers.

\textbf{Memory Overhead.} The tradeoff for $L$-byte padded seqlocks and SoA alignment is increased memory overhead per slot compared to dense tag-based implementations like MemC3. On x86\_64 ($L=64$), fixed per-slot arrays require 96 bytes/slot (64 bytes for \texttt{slotState} + 32 bytes for the four 8-byte \texttt{atomic.Pointer} SoA slices), totaling \textbf{\textasciitilde 96 MB} per million slots before heap-allocated key/payload objects. On Apple Silicon ($L=128$), the 128-byte \texttt{slotState} padding brings fixed array overhead to 160 bytes/slot (\textbf{\textasciitilde 160 MB} per million slots before chunk metadata and key/payload objects), compared to \texttt{otter}'s \textbf{\textasciitilde 120 MB} per million entries.

\textbf{Hit Rate vs.\ True LRU and S3-FIFO.} The Chunked Bitmask algorithm is a 1-bit CLOCK approximation of LRU~\cite{lru1965,clock1969}. As shown in \S\S~9.6 and~9.11, sequential scans larger than capacity evict hot items, workloads exceeding 64 active keys in one set suffer collision evictions even at low global occupancy, and S3-FIFO achieves higher hit rates at tighter capacities or flatter Zipf skew ($s=0.800$).

\textbf{Fixed Capacity.} The cache does not resize and rounds requested capacities up to powers of two (\texttt{nextPowerOfTwo}, minimum 64), requiring callers to provision capacity upfront.

\textbf{Zero-Allocation Scope.} \texttt{Get} guarantees \textbf{0 heap allocations} (verified via \texttt{testing.AllocsPerRun}) on misses and on hits when supplied a caller \texttt{dst} buffer with \texttt{cap(dst) >= len(params)} (including \texttt{nil} when \texttt{len(params) == 0}). \texttt{Add} allocates immutable \texttt{*string} / \texttt{*HandlerFunc} wrappers on miss admissions and fresh \texttt{[]Param} slices when \texttt{len(params) > 0} to preserve race-free single-word \texttt{atomic.Pointer} publication.

\section{Conclusion}

We have presented the hardware-grounded derivation of each principal design decision in \texttt{liteLRU}: off-heap \texttt{mmap} allocation for synchronization metadata combined with single-word \texttt{atomic.Pointer} SoA arrays to immutable Go heap payloads~\cite{gogc2018,gomem2024}; SoA layout to maximize cache-line occupancy per field access~\cite{soasimd2009}; bitset-encoded recency state enabling bulk $\mathcal{O}(1)$ evaluation via hardware \texttt{CTZ} intrinsics~\cite{inteltzcnt,armclz}; monotonic 64-bit Seqlocks~\cite{seqlockoriginal} with $L$-byte cache-line padding~\cite{falsesharing1993,mesi1984} across \texttt{slotState} and \texttt{statStripe} structs; and explicit $W_k$ serialization with $R=10$ admission load-shedding. The resulting architecture delivers race-free concurrency, 19.14M--21.56M effective ops/sec under write-heavy Zipf workloads, and 875~ns 10-run median sampled p99 latency on the baseline harness (\S 9.1, \S 9.7), while openly characterizing non-linearizable writes, set pressure, and 1-bit CLOCK hit-rate limits (\S 9.6, \S 9.11).
